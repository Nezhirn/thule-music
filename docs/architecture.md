# Thule Music — архитектура

Self-hosted музыкальный сервис (по типу Navidrome/Jellyfin): сервер хранит **вашу** библиотеку, клиенты (web, Android, Linux desktop) стримят её. Лицензирование чужого каталога не требуется.

## Ключевые решения

| Тема | Решение | Почему не «как у Spotify» |
|---|---|---|
| Архитектура | Модульный монолит (FastAPI) + отдельный воркер | Микросервисы и Kubernetes оправданы при тысячах инженеров. Модули с чёткими границами можно вынести позже |
| Развёртывание | Один образ (сервер + собранный web-клиент), Docker Compose: `server` + `worker`, Postgres свой или встроенный | K8s/ELK/CDN — когда появится реальная нагрузка |
| БД | PostgreSQL 17, SQLAlchemy 2.1 async, Alembic | — |
| Фоновые задачи | Таблица `jobs` + `SELECT … FOR UPDATE SKIP LOCKED` | Без Redis/брокера; ретраи с экспоненциальной задержкой, дедупликация; выполненные задачи хранятся 7 дней, упавшие — 30 |
| Стриминг | HTTP Range по файлам: оригинал + Opus 160k/96k (ffmpeg) | WebSocket не нужен для аудио по запросу, Icecast/Wowza — для live-радио. HLS — позже при необходимости |
| Auth | Свой JWT: access (15 мин) + refresh с ротацией и детекцией повторного использования (кражей считается только повторно предъявленный уже обменянный токен, и только если с обмена прошло больше 30 секунд; раньше это гонка вкладок или повтор запроса, ответ — `refresh_token_rotated` без закрытия сессий), argon2; не больше 10 неудачных входов за 15 минут на имя пользователя | OIDC (Keycloak/Authentik) можно добавить отдельным способом входа |
| Поиск | `ILIKE` + `pg_trgm` (`word_similarity`) — устойчив к опечаткам | Elasticsearch избыточен для личной библиотеки |
| Тексты | sidecar `.lrc`/`.txt` → тег в файле → LRCLIB; кешируются в БД | Genius/Musixmatch не отдают тексты бесплатно |

## Модули бэкенда (`backend/app`)

```
auth/       пользователи, JWT, refresh-токены; первый зарегистрированный = admin
library/    модели каталога, чтение тегов (mutagen), обложки (Pillow), сканер/импорт, REST каталога
media/      стриминг (Range), подписанные URL, перекодирование ffmpeg, выдача обложек
lyrics/     LRC-парсер, поиск текстов, REST
playlists/  CRUD плейлистов, вставка/перемещение/удаление элементов
me/         лайки треков (виртуальный плейлист «Liked Music»), сохранённые альбомы и артисты, история прослушиваний, настройки пользователя
home/       агрегаты главной: New Releases, Recently played, For You
search/     поиск по артистам/альбомам/трекам
jobs/       очередь, воркер (`python -m app.jobs.worker`), периодическая уборка (раз в 6 ч)
web.py      раздача собранного web-клиента
cli.py      команда `thule`: serve, worker, migrate — запуск в продакшне
```

### Модель данных

`users`, `refresh_tokens` · `artists` (уникальны по нормализованному имени) · `albums` (уникальны по артисту+названию) · `tracks` (идентичность — путь относительно библиотеки) · `track_artists` (все исполнители трека: основной и из «feat.») · `track_files` (перекодированные варианты) · `covers` (дедупликация по sha256, палитра для тонировки UI; здесь же хранятся аватары пользователей) · `lyrics` · `playlists`, `playlist_items` · `track_likes`, `album_likes`, `artist_likes`, `play_events` · `jobs`.

### Конвейер импорта

```
POST /library/scan или /library/uploads
  └─ scan_library: обход папки, сравнение size/mtime с БД, удаление исчезнувших
       └─ import_track (на каждый новый/изменённый файл)
            ├─ теги → upsert artist / album / track (как читаются — ниже)
            ├─ обложка альбома: cover.jpg/folder.png в папке трека или над папкой диска
            │    (CD1, Disc 2), иначе встроенная (по первым трекам)
            │    → миниатюры 64/300/600 и палитра; замену картинки замечает следующий скан
            ├─ transcode: Opus 160k (high) и 96k (low)
            └─ fetch_lyrics: .lrc → тег → LRCLIB (или кеш «нет текста»)
```

Скан запоминает, что нашёл (файлов в папке, добавлено, обновлено, перенесено, удалено) — это результат задачи (`jobs.result`). Уборка хранит последний скан сколько угодно долго, остальные выполненные задачи — неделю. Задача, повтор которой ничего не изменит (файл не аудио или испорчен, `PermanentFailure`), падает сразу, без трёх попыток с паузами; остальные повторяются.

**Загрузка** (`POST /library/uploads`) кладёт файлы в `<библиотека>/uploads/<folder>/`: `folder` — путь папки внутри перетащенного (`Артист/Альбом`), поэтому альбом остаётся вместе, а одинаковые «01.mp3» разных альбомов не сталкиваются. Кроме аудио принимаются обложка альбома (`cover.jpg`, `folder.png`…) и тексты (`.lrc`, `.txt`): скан и импорт находят их рядом с треками. Части пути очищаются (нет `..`, скрытых имён), файл никогда не перезаписывается — занятое имя получает « (1)». Файл, байт в байт совпадающий с треком библиотеки или с файлом рядом, не сохраняется: ответ называет уже лежащий (`duplicate`). Сравнение — sha256 только среди файлов того же размера. Импортируется только аудио; как он идёт, говорит `POST /library/uploads/status` (POST — чтобы влезло много длинных путей).

Файлы текстов (`.lrc`, `.txt` с именем аудиофайла) — не треки, поэтому их отслеживает сам скан: если такой файл появился рядом с треком, который не импортируется заново, изменился после того, как текст был найден, или исчез, а текст был из него, ставится `fetch_lyrics`. Задача, поставленная сканом, сама читает текст из тегов файла.

Теги читаются терпимо к тому, что бывает в реальных файлах:
- **Кодировка.** cp1251 в ID3-кадрах, объявленных как Latin-1, и в Vorbis-комментариях, где байты не UTF-8, читается как кириллица. Настоящий Latin-1 («Café», «Größe») остаётся: текст считается испорченным, только если после перекодировки большинство его букв — кириллица.
- **Исполнители.** «A feat. B», «A ft. B & C», «A (feat. B)», несколько полей ARTIST и «(feat. B)» в названии трека дают основного исполнителя A и приглашённых B, C. Основная часть по «&» не делится, потому что это часть названий групп («Simon & Garfunkel»). Приглашённый артист появляется в каталоге: его страница показывает альбомы, где он участвует. Название трека не меняется. Альбом без ALBUMARTIST, но с COMPILATION=1 считается сборником (Various Artists).
- **Мусор в полях.** Пробелы и управляющие символы схлопываются, пустое значение равно отсутствующему. Год берётся только четырёхзначный. Номер трека или диска 0 считается неизвестным, как и жанр «Unknown». Слишком длинные названия обрезаются до 512 символов, а не роняют импорт.

### Стриминг

- `GET /tracks/{id}/stream?quality=original|high|low` — с заголовком `Authorization` или с подписью.
- `GET /tracks/{id}/stream-url` выдаёт подписанный URL (HMAC, 6 часов) — для `<audio src>` и ExoPlayer. URL относительный (`/api/v1/tracks/…`): клиент дополняет его адресом сервера, поэтому он не зависит от заголовков обратного прокси. URL **привязан к уже существующему варианту файла**: если перекодирование ещё не готово, отдаётся оригинал. Иначе Range-запросы посреди трека начали бы читать другой файл. В ответе есть и то, что URL играет: кодек и битрейт (`opus`, 160 — у перекодировки; кодек и битрейт файла — у оригинала).
- `POST /me/plays` — прослушивание (скроббл): `track_id` и сколько послушали. Из них строятся «Недавно слушали», «Для вас» и история.
- `GET /me/history` — история: каждое прослушивание, новые первыми. Страницы листаются от последнего прослушивания предыдущей (`before`), а не по смещению, поэтому прослушивания, записанные во время чтения, не сдвигают страницы. `DELETE /me/history` стирает историю, а с ней «Недавно слушали» и то, что «Для вас» узнало из прослушиваний.
- `GET /search?q=` — артисты, альбомы и треки: подстрока или похожее слово (`pg_trgm`), ближайшие первыми; альбомы и треки — и по имени артиста. С `type` (`artists`, `albums`, `tracks`) — только этот вид, страницами через `limit` и `offset`.
- `GET /tracks/{id}/lyrics` — текст трека: `plain` и строки с таймкодами (`lines`, если текст синхронный), источник, «инструментал»; `lyrics_not_found`, если текста нет.
- Обложки `GET /covers/{id}?size=` — публичные (UUID неугадываем), `Cache-Control: immutable`.

### Администрирование

Только для администраторов (`admin_only` остальным):
- `GET /library/stats` — артистов, альбомов, треков, общая длительность и размер файлов.
- `POST /library/scan` ставит скан (если он уже ждёт или идёт — возвращает его), `GET /library/scan` — последний скан: статус, что нашёл, и `imports` — счётчики импортов, поставленных с его начала. Они читаются вместе со статусом, поэтому скан, который уже «done», всегда приходит с поставленными им импортами, и прогресс не может на мгновение показать «всё готово».
- `GET /library/jobs` — задачи страницами, по статусу и виду, с `subject`: о чём задача по-человечески (файл импорта, «Артист — Трек», «Артист — Альбом»). `POST /library/jobs/{id}/retry` и `POST /library/jobs/retry` запускают упавшие заново с первой попытки (повтор ставится как новая задача, если такая же уже не ждёт), `DELETE /library/jobs/failed` забывает упавшие. `GET /library/jobs/summary` — сколько задач каждого вида ждёт, выполняется и упало.
- `GET /users` — пользователи с `last_seen_at` (вход или обновление токенов: раз в несколько минут, пока клиент открыт) и числом активных сеансов (непросроченных refresh-токенов). `DELETE /users/{username}/sessions` завершает все сеансы, `POST /users/{username}/password` задаёт пароль (и тоже завершает сеансы), `PATCH` меняет роль, `DELETE` удаляет. Себе роль не сменить и себя не удалить — администратор на сервере остаётся всегда.

### Продакшн

- **Запуск.** `thule serve` (uvicorn) и `thule worker` сначала ждут базу (до минуты; неверный пароль или имя базы — сразу ошибка), затем выполняют `alembic upgrade head` отдельным процессом и проверяют папки: в папку данных нужно писать, иначе запуск останавливается с подсказкой про владельца; в папку с музыкой — желательно, иначе в логе предупреждение, что не будет работать загрузка. Миграции идут под advisory-блокировкой Postgres, взятой до `CREATE SCHEMA`: сервер и воркер стартуют одновременно, и без неё на новой базе второй падал на создании тех же объектов. `thule` ставит обработчик SIGTERM до запуска сервера: в контейнере это процесс 1, и без обработчика `docker stop` ждал бы принудительного завершения.
- **Образ** (`Dockerfile` в корне): web-клиент собирается в Node, зависимости сервера ставятся `uv sync --frozen` из `uv.lock` — те же версии, что в тестах. Итоговый образ — `python:3.13-slim` с ffmpeg. `docker/entrypoint.sh` стартует от root: отдаёт `PUID:PGID` папку данных и созданную им папку `uploads/` и запускает команду от этого пользователя (`setpriv`), с `HOME=/nonexistent`. Иначе драйвер Postgres упирался бы в закрытый `/root`, ища там клиентские сертификаты.
- **Раздача web-клиента** (`THULE_WEB_PATH`). Обработчик стоит запасным маршрутом роутера, а не смонтирован на «/»: так известный путь API с неверным методом получает 405, а не 404. Путь без расширения вне `/assets` считается страницей приложения и получает `index.html`. Неизвестный путь под `/api` и несуществующий файл (`/assets/…` или путь с расширением, как `/favicon.ico`) получают 404 в формате ошибок API: пропавший скрипт не должен вернуться страницей. `/assets/*` — `immutable` на год, остальное — `no-cache` с ETag. Сжатые копии (`.br`, `.gz`) делает плагин сборки Vite, сервер выбирает их по `Accept-Encoding` и ставит `Vary`. Библиотеки собираются в отдельный файл: при обновлении приложения браузер скачивает заново только его код.
- **Content Security Policy** на страницах: всё только со своего origin, без inline-стилей и inline-скриптов (хеши встроенных в `index.html` скриптов, если они там появятся, сервер добавит в политику сам), `object-src 'none'`, `frame-ancestors 'none'`. Refresh-токен лежит в localStorage, и политика — то, что не даёт внедрённому скрипту его унести. E2E падает на любом нарушении политики.
- **Запись в библиотеку.** Загрузка в папку только для чтения или без прав отвечает `library_not_writable` (503), при кончившемся месте — `disk_full` (507), а не 500.

## API

Префикс `/api/v1`, интерактивная документация — `/api/docs`, схема — `/api/openapi.json`: всё серверное лежит под `/api`, остальные пути принадлежат web-клиенту. OpenAPI — контракт для web-клиента (генерация TS-типов) и KMP-клиента. Поле ответа со значением по умолчанию в схеме обязательное, потому что в JSON оно есть всегда. В запросах такие поля необязательные. Так сгенерированные клиенты получают точные типы.

Ошибки — всегда `{"code": ..., "detail": ...}`. `code` — стабильный идентификатор из перечисления `ErrorCode` (`invalid_credentials`, `track_not_found`, …): по нему клиенты показывают переведённое сообщение. `detail` — английский текст для разработчика, а у ошибок валидации (`validation_error`, 422) — список полей с `loc` и `type`.

## Клиенты (следующие фазы)

**Web (фаза 2):** React + Vite + TypeScript, TanStack Query, типы из OpenAPI, CSS `backdrop-filter` для стекла, `<audio>` + Media Session API. Код лежит в `web/`. Dev-сервер Vite проксирует `/api` на бэкенд, поэтому браузер работает с одним origin, как в продакшне, где сборку раздаёт сам сервер.

### Web-плеер

Один элемент `<audio>` на всё приложение (`web/src/player/player.ts`), состояние — в Zustand-хранилище, которое читают плеер внизу, «Сейчас играет», строки таблиц и кнопки «Играть». Логика очереди (`queue.ts`) — чистые функции с тестами; элемент `<audio>` в тестах заменяется подделкой, которая шлёт события так же, как браузер.
- **Поток.** Ссылка (`stream-url`) запрашивается перед воспроизведением трека, в выбранном в настройках качестве. Браузеру без Ogg Opus (`canPlayType`) — сразу оригинал. Если ссылка истекает в течение минуты, перед продолжением берётся новая. Если поток оборвался (истёкшая ссылка, сеть), ссылка запрашивается заново один раз и трек продолжается с той же секунды; если и это не помогло, трек пропускается. После трёх неудач подряд плеер останавливается. Если же на запрос ссылки сервер не ответил вовсе (нет сети, страницу перезагружают или закрывают), плеер останавливается на этом треке, а не пропускает его: иначе перезагрузка в момент старта трека возвращала бы очередь на следующем. Ответ на запрос ссылки для трека, который уже не нужен (быстро нажали «Следующий»), отбрасывается. Смена качества в настройках применяется к играющему треку сразу.
- **Скроббл.** Прослушиванием считается реально проигранное время, без перемоток и пауз: после 30 секунд (у трека короче минуты — после половины) плеер отправляет `POST /me/plays`. Повтор трека — новое прослушивание.
- **Очередь** хранится на устройстве (localStorage): после перезагрузки она на месте, на паузе с той же секунды. При выходе из аккаунта очередь стирается. Громкость — настройка устройства, она остаётся. Синхронизация очереди между устройствами — вместе с Android.
- **Media Session**: название, исполнитель, альбом и обложка на экране блокировки и в системных медиа-кнопках, оттуда же — пауза, переключение и перемотка.

### Моё в web

- **Лайки** (`web/src/likes/`) применяются сразу. Изменённые на этом устройстве хранятся поверх поля `liked` уже загруженных страниц, пока те не загрузятся заново. Треки в очереди плеера обновляются тоже, поэтому после перезагрузки лайк на месте. Изменения одного трека, альбома или артиста уходят на сервер строго по очереди: иначе «лайк» и «снять лайк» могли бы прийти в обратном порядке. Если сервер отказал, возвращается прежнее значение, если пользователь не успел изменить его снова. Списки «Любимые треки» и «Избранное» перезагружаются после ответа сервера.
- **Плейлисты** (`web/src/playlists/`): перестановка и удаление трека видны сразу. Изменения одного плейлиста уходят по очереди, и плейлист от сервера заменяет показанный, когда пришёл ответ на последнее изменение. Если изменение не прошло, плейлист загружается заново. Один трек может быть в плейлисте и в истории несколько раз, поэтому строки таблицы различаются по `item_id` и id прослушивания, а не по треку.

### Поиск в web

- Запрос уходит через 250 мс после последней нажатой клавиши или сразу по Enter. Запрос, который перебил следующий, отменяется (`AbortSignal`), а прежние результаты остаются на экране приглушёнными, пока не придут новые.
- Лучшее совпадение выбирает клиент (`web/src/search/match.ts`) из первых артиста, альбома и трека: название, равное запросу, лучше начинающегося с него, а то — лучше слова, начинающегося с него. Сравнение без учёта регистра, ударений и разницы «ё»/«е», но «й» остаётся собой.
- Плейлисты свои и немногочисленные: их ищет клиент по уже загруженному списку.

### Администрирование в web

- **Прогресс скана** берётся из `GET /library/scan` (статус и импорты одним ответом); пока скан или его импорты не закончены, он и сводка задач запрашиваются раз в секунду, потом опрос останавливается. Когда скан, начатый или замеченный на странице, закончился, перезагружаются каталог, главная и поиск, а итог объявляется. Если скан ждёт обработчик дольше 10 секунд, страница подсказывает проверить, что worker запущен.
- **Загрузка** (`web/src/admin/uploads.ts`) — очередь вне React, поэтому она продолжается, пока администратор ходит по приложению, и останавливается при выходе. Файлы уходят по два, через `XMLHttpRequest` — только он сообщает, сколько отправлено. Обложки и тексты папки уходят раньше её треков, чтобы импорт их уже застал. После отправки статус импорта спрашивается раз в полторы секунды, пачками до 100 путей. Перетащенные папки читаются через `webkitGetAsEntry`, выбранные — через `webkitdirectory`. Скрытые файлы и то, что не музыка, не обложка и не текст рядом с треком, пропускаются ещё на клиенте. Пока файлы в пути, закрытие вкладки спрашивает подтверждение.

**Android + Linux (фаза 3):** Kotlin Multiplatform + Compose Multiplatform, Ktor-клиент, blur — Haze. Android: Media3/ExoPlayer + `MediaSessionService`. Linux: VLCJ или GStreamer (выбрать прототипом), MPRIS через D-Bus.

### Дизайн

Минимализм + glassmorphism по референсу. Поправки:
- вторичный текст на стекле — проверять контраст WCAG AA (≥ 4.5:1);
- на Linux — без macOS-кнопок окна;
- мобильный лэйаут отдельный: нижняя навигация, полноэкранный плеер;
- размытие: Android < 12 и GNOME не умеют системный blur — размываем обложку внутри приложения;
- `cover_palette` из API — для тонировки фона под текущий трек: `average`, `dominant`, `muted` (спокойный), `vibrant` (самый яркий; `null` у серых обложек), `luminance`. Web берёт `vibrant` (у серых обложек — `dominant`), `dominant` и `muted`, приглушает их и кладёт тремя пятнами под стекло; акцент остаётся выбранным пользователем. На страницах альбома и артиста тот же приглушённый цвет обложки слабо подкрашивает верх панели. Как при этом держится контраст — в [roadmap.md](roadmap.md#фаза-2--web-клиент), абзац «Тема».

## Риски

- **Задержка до БД.** Postgres доступен по сети (~80 мс на запрос, ~1,3 с на новое соединение). Пул соединений обязателен; API лучше разворачивать рядом с БД.
- **Аудио на Linux в JVM** не работает «из коробки» — нужен прототип.
- **Большая библиотека** долго перекодируется. Оригинал доступен сразу, варианты появляются по мере обработки очереди.
