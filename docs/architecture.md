# Thule Music — архитектура

Self-hosted музыкальный сервис (по типу Navidrome/Jellyfin): сервер хранит **вашу** библиотеку, клиенты (web, Android, Linux desktop) стримят её. Лицензирование чужого каталога не требуется.

## Ключевые решения

| Тема | Решение | Почему не «как у Spotify» |
|---|---|---|
| Архитектура | Модульный монолит (FastAPI) + отдельный воркер | Микросервисы и Kubernetes оправданы при тысячах инженеров. Модули с чёткими границами можно вынести позже |
| Развёртывание | Один образ (сервер + собранный web-клиент), Docker Compose: `server` + `worker`, Postgres свой или встроенный | K8s/ELK/CDN — когда появится реальная нагрузка |
| БД | PostgreSQL 17, SQLAlchemy 2.1 async, Alembic | — |
| Фоновые задачи | Таблица `jobs` + `SELECT … FOR UPDATE SKIP LOCKED` | Без Redis/брокера; ретраи с экспоненциальной задержкой, дедупликация; выполненные задачи хранятся 7 дней, упавшие — 30 |
| Стриминг | HTTP Range по файлам: оригинал + Opus 160k/96k (ffmpeg) | WebSocket не нужен для аудио по запросу, Icecast/Wowza — для live-радио. HLS — позже при необходимости |
| Auth | Свой JWT: access (15 мин) + refresh с ротацией и детекцией повторного использования, argon2; не больше 10 неудачных входов за 15 минут на имя пользователя. Новый refresh-токен выводится из старого секретом сервера. Если старый предъявили снова, пока новый ни разу не использован, сервер возвращает тот же ответ: ответ на обмен потерялся (закрыли страницу, пропала сеть) или его одновременно обменивает другая вкладка. Кражей считается старый токен, предъявленный после того, как новый уже использован, и позже 30 секунд; в эти 30 секунд это гонка вкладок, ответ — `refresh_token_rotated` без закрытия сессий. Access-токен, действительный в момент начала запроса, годится на весь запрос: тело загрузки читается до проверки токена, а большой файл может грузиться дольше, чем живёт токен. Клиент ждёт ответа на вход и обновление не дольше 15 секунд, потом считает сервер недоступным, а сессию сохраняет | OIDC (Keycloak/Authentik) можно добавить отдельным способом входа |
| Поиск | `ILIKE` + `pg_trgm` (`word_similarity`) — устойчив к опечаткам | Elasticsearch избыточен для личной библиотеки |
| Тексты | sidecar `.lrc`/`.txt` → тег в файле → LRCLIB; кешируются в БД | Genius/Musixmatch не отдают тексты бесплатно |

## Модули бэкенда (`backend/app`)

```
auth/       пользователи, JWT, refresh-токены; первый зарегистрированный = admin
library/    модели каталога, чтение и запись тегов (mutagen), обложки (Pillow), сканер/импорт, REST каталога, управление медиатекой
media/      стриминг (Range), подписанные URL, перекодирование ffmpeg, выдача обложек
lyrics/     LRC-парсер, поиск текстов, REST
playlists/  CRUD плейлистов, вставка/перемещение/удаление элементов
me/         лайки треков (виртуальный плейлист «Liked Music»), сохранённые альбомы и артисты, история прослушиваний, настройки пользователя
home/       агрегаты главной: New Releases, Recently played, For You
search/     поиск по артистам/альбомам/трекам
jobs/       очередь, воркер (`python -m app.jobs.worker`), периодическая уборка (раз в 6 ч)
web.py      раздача собранного web-клиента
cli.py      команда `thule`: serve, worker, migrate — запуск в продакшне
```

### Модель данных

`users`, `refresh_tokens` · `artists` (уникальны по нормализованному имени; `cover_id` — фото от администратора) · `albums` (уникальны по артисту+названию; `cover_custom` — обложку выбрал администратор) · `tracks` (идентичность — путь относительно библиотеки; `cover_id` — своя картинка трека от администратора) · `track_artists` (все исполнители трека: основной и из «feat.») · `track_files` (перекодированные варианты) · `covers` (дедупликация по sha256, палитра для тонировки UI; здесь же хранятся обложки треков и аватары пользователей) · `lyrics` · `playlists`, `playlist_items` · `track_likes`, `album_likes`, `artist_likes`, `play_events` · `jobs`.

### Конвейер импорта

```
POST /library/scan или /library/uploads
  └─ scan_library: обход папки, сравнение size/mtime с БД, удаление исчезнувших
       └─ import_track (на каждый новый/изменённый файл)
            ├─ теги → upsert artist / album / track (как читаются — ниже)
            ├─ обложка альбома: cover.jpg/folder.png в папке трека или над папкой диска
            │    (CD1, Disc 2), иначе встроенная (по первым трекам)
            │    → миниатюры 64/300/600 и палитра; замену картинки замечает следующий скан;
            │    обложку, выбранную администратором, не трогает
            ├─ transcode: Opus 160k (high) и 96k (low); пока идёт ffmpeg, транзакция не открыта; если файл изменился за это время, задача повторяется
            └─ fetch_lyrics: .lrc → тег → LRCLIB (или кеш «нет текста»); текст от администратора не трогает
```

Скан запоминает, что нашёл (файлов в папке, добавлено, обновлено, перенесено, удалено) — это результат задачи (`jobs.result`).

**Очередь задач.**
- **Живой воркер.** Пока задача выполняется, её воркер раз в минуту отмечается в строке задачи (`locked_at`). Задачу, о которой не слышно 5 минут, другой воркер считает брошенной и берёт снова: её процесс убили, кончилась память или контейнер остановлен. Поэтому скан не висит «выполняется» полчаса после рестарта.
- **Остановка.** Получив SIGTERM, воркер даёт текущей задаче 20 секунд закончить, потом останавливает её (ffmpeg убивается) и возвращает в очередь. Прерванная попытка не считается, и следующий воркер берёт задачу сразу. Docker ждёт 30 секунд (`stop_grace_period`).
- **Чужая задача.** Отметки «готово», «упала» и «жив» пишет только тот воркер, который задачу сейчас держит. Опоздавший воркер, которого сочли мёртвым, не затрёт работу следующего.
- **Отложенные задачи.** Задача может попросить запустить её позже (`Postpone`), когда нужный ей сервис недоступен. Попытка при этом не считается.
- **LRCLIB.** Если он не отвечает, отвечает 5xx или 429, поиск текстов откладывается на 5 минут, потом на 10 и так далее, но не дольше часа, а не проваливается у каждого трека по очереди. На соединение отводится 5 секунд. Найденный однажды текст не стирается, если по новому названию альбома его больше не находят. Правки, которые не меняют название, исполнителя или альбом (жанр, год, номер), тексты заново не ищут.
- **База недоступна.** Воркер пишет об этом один раз полностью, дальше коротко, и пробует снова с паузой, растущей до минуты.

**Скан не стирает медиатеку из-за отключённого диска.** Удалить трек значит удалить и его лайки, места в плейлистах и историю, поэтому трек удаляется, только если его файла точно нет:
- Треки в папках, которые не удалось прочитать (нет прав, ошибка диска, ссылка на отключённый диск), остаются. Скан называет их число (`unreadable`).
- Если в папке нет ни одного аудиофайла или пропало больше 50 треков и больше пятой части медиатеки сразу, скан ничего не удаляет и называет, сколько не нашёл (`missing`). Скорее всего, диск не подключён, а не музыка удалена. Администратор видит это на странице «Медиатека» и может удалить их кнопкой. Это скан с `remove_missing`.
- Медиатека читается из базы до обхода папки. Файл, импортированный или перенесённый во время обхода, окажется в худшем случае «новым», но не «удалённым».
- Импорт отдельного файла тоже не удаляет трек, если папка с музыкой пуста. Задача падает и повторяется позже.

**Уборка** (`housekeeping`, раз в 6 часов) удаляет обложки, на которые больше ничто не ссылается, вместе с их файлами. Файлы в `covers/` и `transcodes/`, которых не знает ни одна строка базы, она удаляет только как исключение. Если таких больше 20 и больше половины всех файлов, папка пропускается, а в логе появляется предупреждение. Так же пропускаются перекодировки, если в базе нет ни одного трека. Пустая или чужая база (ещё восстанавливается, ошиблись адресом) иначе выглядела бы так, будто все файлы лишние, а в `covers/` лежат единственные копии обложек и фото, загруженных вручную. Пропавшие файлы делаются заново по требованию. Обложка из файлов музыки выбирается заново при первом запросе её картинки. Перекодировка ставится заново, когда трек просят сыграть: до этого играет оригинал. Тот же sha256 при повторной загрузке картинки перерисовывает пропавшие файлы. Уборка хранит последний скан сколько угодно долго, остальные выполненные задачи — неделю. Задача, повтор которой ничего не изменит (файл не аудио или испорчен, `PermanentFailure`), падает сразу, без трёх попыток с паузами; остальные повторяются.

**Загрузка** (`POST /library/uploads`) кладёт файлы в `<библиотека>/uploads/<folder>/`: `folder` — путь папки внутри перетащенного (`Артист/Альбом`), поэтому альбом остаётся вместе, а одинаковые «01.mp3» разных альбомов не сталкиваются. Кроме аудио принимаются обложка альбома (`cover.jpg`, `folder.png`…) и тексты (`.lrc`, `.txt`): скан и импорт находят их рядом с треками. Части пути очищаются (нет `..`, скрытых имён, не длиннее 200 байт), файл никогда не перезаписывается — занятое имя получает « (1)». Файл, байт в байт совпадающий с треком библиотеки или с файлом рядом, не сохраняется: ответ называет уже лежащий (`duplicate`). Сравнение — sha256 только среди файлов того же размера; файлы одной папки сверяются по одному, иначе две одинаковые картинки, загруженные одновременно, нашли бы друг друга и удалились обе. Импортируется только аудио; как он идёт, говорит `POST /library/uploads/status` (POST — чтобы влезло много длинных путей).

Файлы текстов (`.lrc`, `.txt` с именем аудиофайла) — не треки, поэтому их отслеживает сам скан: если такой файл появился рядом с треком, который не импортируется заново, изменился после того, как текст был найден, или исчез, а текст был из него, ставится `fetch_lyrics`. Задача, поставленная сканом, сама читает текст из тегов файла.

Теги читаются терпимо к тому, что бывает в реальных файлах:
- **Кодировка.** cp1251 в ID3-кадрах, объявленных как Latin-1, и в Vorbis-комментариях, где байты не UTF-8, читается как кириллица. Настоящий Latin-1 («Café», «Größe») остаётся: текст считается испорченным, только если после перекодировки большинство его букв — кириллица.
- **Исполнители.** «A feat. B», «A ft. B & C», «A (feat. B)», несколько полей ARTIST и «(feat. B)» в названии трека дают основного исполнителя A и приглашённых B, C. Основная часть по «&» не делится, потому что это часть названий групп («Simon & Garfunkel»). Приглашённый артист появляется в каталоге: его страница показывает альбомы, где он участвует. Название трека не меняется. Альбом без ALBUMARTIST, но с COMPILATION=1 считается сборником (Various Artists).
- **Мусор в полях.** Пробелы и управляющие символы схлопываются, пустое значение равно отсутствующему. Год берётся только четырёхзначный. Номер трека или диска 0 считается неизвестным, как и жанр «Unknown». Слишком длинные названия обрезаются до 512 символов, а не роняют импорт.

### Стриминг

- `GET /tracks/{id}/stream?quality=original|high|low` — с заголовком `Authorization` или с подписью.
- `GET /tracks/{id}/stream-url` выдаёт подписанный URL (HMAC, 6 часов) — для `<audio src>` и ExoPlayer. URL относительный (`/api/v1/tracks/…`): клиент дополняет его адресом сервера, поэтому он не зависит от заголовков обратного прокси. URL **привязан к уже существующему варианту файла**: если перекодирование ещё не готово, отдаётся оригинал. Иначе Range-запросы посреди трека начали бы читать другой файл. В ответе есть и то, что URL играет: кодек и битрейт (`opus`, 160 — у перекодировки; кодек и битрейт файла — у оригинала).
- `POST /me/plays` — прослушивание (скроббл): `track_id` и сколько послушали. Из них строятся «Недавно слушали», «Для вас» и история.
- `GET /me/history` — история: каждое прослушивание, новые первыми. Страницы листаются от последнего прослушивания предыдущей (`before`), а не по смещению, поэтому прослушивания, записанные во время чтения, не сдвигают страницы. `DELETE /me/history` стирает историю, а с ней «Недавно слушали» и то, что «Для вас» узнало из прослушиваний.
- `GET /search?q=` — артисты, альбомы и треки: подстрока или похожее слово (`pg_trgm`), ближайшие первыми; альбомы и треки — и по имени артиста. С `type` (`artists`, `albums`, `tracks`) — только этот вид, страницами через `limit` и `offset`.
- `GET /tracks/{id}/lyrics` — текст трека: `plain` и строки с таймкодами (`lines`, если текст синхронный), источник (`sidecar`, `embedded`, `lrclib`, `manual`), «инструментал»; `lyrics_not_found`, если текста нет.
- Картинка трека в `TrackOut` (`cover_id`, `cover_palette`) — его собственная, если её задал администратор, иначе обложка альбома; `album.cover_id` — всегда обложка альбома. Клиенты показывают у трека `cover_id`, у альбома — обложку альбома. Мозаика плейлиста тоже собирается из картинок треков.
- Обложки `GET /covers/{id}?size=` — публичные (UUID неугадываем), `Cache-Control: immutable`.

### Администрирование

Только для администраторов (`admin_only` остальным):
- `GET /library/stats` — артистов, альбомов, треков, общая длительность и размер файлов.
- `POST /library/scan` ставит скан (если он уже ждёт или идёт — возвращает его), `GET /library/scan` — последний скан: статус, что нашёл, и `imports` — счётчики импортов, поставленных с его начала. Они читаются вместе со статусом, поэтому скан, который уже «done», всегда приходит с поставленными им импортами, и прогресс не может на мгновение показать «всё готово».
- `GET /library/jobs` — задачи страницами, по статусу и виду, с `subject`: о чём задача по-человечески (файл импорта, «Артист — Трек», «Артист — Альбом»). `POST /library/jobs/{id}/retry` и `POST /library/jobs/retry` запускают упавшие заново с первой попытки (повтор ставится как новая задача, если такая же уже не ждёт), `DELETE /library/jobs/failed` забывает упавшие. `GET /library/jobs/summary` — сколько задач каждого вида ждёт, выполняется и упало.
- **Правки.** `PUT /tracks/{id}/lyrics` (`text`, `instrumental`) — текст от администратора, источник `manual`: пустой текст значит «у трека нет текста», LRC с таймкодами принимается. Скан, импорт и `fetch_lyrics` такой текст не перезаписывают; запись задачи защищена условием в самом `ON CONFLICT`, поэтому поиск, уже шедший в момент правки, её не затрёт. `DELETE` забывает текст (любой) и ставит `fetch_lyrics` заново (202); веб после этого несколько раз за ~15 секунд спрашивает текст и сообщает, нашёлся ли он. `PUT /albums/{id}/cover` (multipart, JPEG/PNG/WebP до 20 МБ) ставит обложку и `cover_custom`: выбор обложки по файлам её больше не меняет. Выбор обложки при импорте берёт строку альбома `FOR UPDATE`: правка, пришедшая в тот же момент, ждёт его и записывается последней, а импорт, начавшийся после правки, её видит. `DELETE` возвращает выбор файлам и сразу выбирает обложку заново. `PUT`/`DELETE /tracks/{id}/cover` — своя картинка трека и её сброс. Уборка не удаляет обложки, на которые ссылаются треки.
- **Управление медиатекой** (`app/library/manage.py`): `PATCH /albums/{id}` (title, artist, year, genre), `DELETE /albums/{id}?tracks=delete|singles`, `POST /albums/{id}/tracks` (файл), `PATCH /tracks/{id}` (title, artists, track_no, disc_no), `DELETE /tracks/{id}`, `POST /tracks/move` (`track_ids` и `album_id` или `new_album`), `PATCH /artists/{id}` (name), `DELETE /artists/{id}`, `POST /artists/{id}/tracks` (файл и `album`, `year`, `genre`), `POST /albums/move` (`album_ids` и `artist`), `PATCH /genres?genre=` (name), `POST /albums/genre` (`album_ids` и `genre`), `DELETE /genres?genre=&albums=keep|delete`. Фото исполнителя (`PUT`/`DELETE /artists/{id}/cover`) — в `app/library/edits.py` рядом с обложками: в файлах ему места нет, оно хранится только на сервере, а без него показывается обложка последнего альбома. Каждая операция сначала меняет файлы — теги (`app/library/tagwrite.py`, теми же «easy»-ключами mutagen, какими их читает импорт; несколько исполнителей — несколькими значениями ARTIST, чтобы «A & B» не распалось; оборванная запись — убитый процесс, отключённое питание — не должна портить файл: теги, которые помещаются в запас, оставленный под них в файле (padding), MP3 и FLAC переписывают на месте одной записью, которую убитый процесс не прерывает; иначе аудио пришлось бы сдвигать, и теги пишутся в копию рядом с файлом, скрытую `.thule-….flac`, с запасом на следующие правки, которая после `fsync` заменяет его `os.replace`; копия не делается, только если она не может быть такой же: у файла жёсткие ссылки, другой владелец, которого серверу не выставить, папка без права записи, нет места на копию; копии, оставшиеся от оборванных записей, скан убирает через час), папки (`app/library/files.py`: перенос вместе с `.lrc`/`.txt`, свободное имя «x (1)», имена не длиннее 200 байт, уборка папок, где не осталось музыки — только обложка и мусор файловых менеджеров; уборка идёт после коммита и не трогает `uploads/`: если папку не удалось убрать, сделанное не откатывается) — и сразу заново импортирует изменённые файлы (`import_file`, общий с задачей импорта): в базе то, что увидел бы скан, и следующий скан ничего не меняет. Альбом и исполнитель переименовываются на месте, до импорта, поэтому их id, лайки и ссылки сохраняются; имя другого альбома (того же исполнителя) или исполнителя объединяет их, лайки переносятся. Удаление «синглами» переписывает у треков альбом на название трека и исполнителя альбома на основного исполнителя, без номеров; файлы остаются в папке и делят её обложку, а синглу без своей обложки достаётся обложка удалённого альбома. Перенесённый файл ложится рядом с треками того же диска целевого альбома (иначе — рядом с первым), чтобы обложка папки не перепутала альбомы. Только перезапись тегов не ставит перекодирование. Если запись не удалась посреди операции (файл только для чтения, место), уже записанные файлы импортируются и коммитятся, ошибка возвращается: база не расходится с папкой. Форматы без записываемых тегов (WAV, WMA, AAC) — `tags_not_writable` до того, как что-то изменилось. Альбомы, отданные другому исполнителю, остаются в своих папках: меняются исполнитель альбома и, где он был исполнителем трека, — исполнитель трека (и «feat.» в названии); альбом с тем же названием у нового исполнителя объединяется с переносимым. Удаление исполнителя удаляет файлы его треков и треков его альбомов, а из чужих треков, где он только приглашён, убирает его имя (из ARTIST и из «feat.» в названии) — сначала это, чтобы при ошибке записи ничего не было удалено; «передать другому исполнителю» в интерфейсе — это переименование в его имя. Альбом, загруженный исполнителю, находится по названию среди его альбомов, а новый ложится в `<исполнитель>/<альбом>/`; папка, созданная для файла, который не сохранился (копия, не аудио), убирается. Жанр — у альбома (`albums.genre`), поэтому переименование, перенос в другой жанр и снятие жанра пишут его в теги всех треков этих альбомов и ставят альбомам сразу: импорт берёт жанр у альбома, только если его ещё нет. Написания жанра, различающиеся регистром, — один жанр, как в `GET /genres`, так что переименование их и объединяет. Жанр передаётся параметром запроса, а не в пути: в названиях бывает «/» («Hip-Hop/Rap»). Старые FLAC с байтами не в UTF-8 при записи получают основные теги заново, исправленными, иначе mutagen сохранил бы их как U+FFFD. Массовые правки не держат транзакцию, пока пишутся файлы (на это уходят минуты, а база закрывает простаивающую транзакцию через 30 секунд), и заново импортируют файлы пачками по 200 в отдельных транзакциях. Жанр — свойство альбома, поэтому при его смене у треков меняются только размер и время файла. Их сервер записывает одним запросом на все треки, без импорта каждого файла: переименование жанра на 3000 треков — около 17 запросов, а не 36 000. Так же переименовывается исполнитель, если это не слияние с другим: у треков меняются только «feat.» в названии, размер и время файла. Тексты при этом заново ищутся только для треков, у которых их ещё не нашли. Заново импортируется только файл, изменившийся на диске с последнего скана. Правки идемпотентны: повтор после обрыва связи доделывает только то, что не успело.
- `GET /users` — пользователи с `last_seen_at` (вход или обновление токенов: раз в несколько минут, пока клиент открыт) и числом активных сеансов (непросроченных refresh-токенов). `DELETE /users/{username}/sessions` завершает все сеансы, `POST /users/{username}/password` задаёт пароль (и тоже завершает сеансы), `PATCH` меняет роль, `DELETE` удаляет. Себе роль не сменить и себя не удалить — администратор на сервере остаётся всегда.

### Продакшн

- **Запуск.** `thule serve` (uvicorn) и `thule worker` сначала ждут базу (до минуты; неверный пароль или имя базы — сразу ошибка), затем выполняют `alembic upgrade head` отдельным процессом и проверяют папки: в папку данных нужно писать, иначе запуск останавливается с подсказкой про владельца; в папку с музыкой — желательно, иначе в логе предупреждение, что не будет работать загрузка. Миграции идут под advisory-блокировкой Postgres, взятой до `CREATE SCHEMA`: сервер и воркер стартуют одновременно, и без неё на новой базе второй падал на создании тех же объектов. `thule` ставит обработчик SIGTERM до запуска сервера: в контейнере это процесс 1, и без обработчика `docker stop` ждал бы принудительного завершения.
- **Образ** (`Dockerfile` в корне): web-клиент собирается в Node, зависимости сервера ставятся `uv sync --frozen` из `uv.lock` — те же версии, что в тестах. Итоговый образ — `python:3.13-slim` с ffmpeg. `docker/entrypoint.sh` стартует от root: отдаёт `PUID:PGID` папку данных и созданную им папку `uploads/` и запускает команду от этого пользователя (`setpriv`), с `HOME=/nonexistent`. Иначе драйвер Postgres упирался бы в закрытый `/root`, ища там клиентские сертификаты.
- **Раздача web-клиента** (`THULE_WEB_PATH`). Обработчик стоит запасным маршрутом роутера, а не смонтирован на «/»: так известный путь API с неверным методом получает 405, а не 404. Путь без расширения вне `/assets` считается страницей приложения и получает `index.html`. Неизвестный путь под `/api` и несуществующий файл (`/assets/…` или путь с расширением, как `/favicon.ico`) получают 404 в формате ошибок API: пропавший скрипт не должен вернуться страницей. `/assets/*` — `immutable` на год, остальное — `no-cache` с ETag. Сжатые копии (`.br`, `.gz`) делает плагин сборки Vite, сервер выбирает их по `Accept-Encoding` и ставит `Vary`. Библиотеки собираются в отдельный файл: при обновлении приложения браузер скачивает заново только его код.
- **Content Security Policy** на страницах: всё только со своего origin, без inline-стилей и inline-скриптов (хеши встроенных в `index.html` скриптов, если они там появятся, сервер добавит в политику сам), `object-src 'none'`, `frame-ancestors 'none'`. Refresh-токен лежит в localStorage, и политика — то, что не даёт внедрённому скрипту его унести. E2E падает на любом нарушении политики.
- **База и сбои связи с ней.**
  - **Соединение отдаётся в пул до отправки тела ответа.** Сессия БД закрывается, как только обработчик закончил (`Depends(get_session, scope="function")`), поэтому трек, который медленный слушатель качает минутами, не держит соединение.
  - **Пул API** — 10 соединений и ещё 10 при нагрузке. Запрос ждёт свободное соединение не дольше 10 секунд, потом получает 503 `service_unavailable` с `Retry-After`.
  - **Таймауты.** Запрос к базе дольше 30 секунд отменяется. Соединение, простоявшее в открытой транзакции дольше 30 секунд, база закрывает. Клиент не ждёт ответа дольше 35 секунд, а соединения — дольше 10. Значения задаются переменными `THULE_DB_*`.
  - **Мёртвые соединения.** Перед использованием соединение проверяется (`pool_pre_ping`) и не живёт дольше получаса: соединение, которое забыл NAT или разорвала перезапущенная база, не подвешивает запрос.
  - **Воркер** проверяет соединения так же. Ограничено только время подключения: его задачи бывают долгими.
  - **Формат ошибок.** Обрыв связи с базой, отмена по таймауту и занятый пул дают 503 `service_unavailable`. Изменение, столкнувшееся с другим одновременным, даёт 409 `conflict`. Любая другая ошибка даёт 500 `internal_error`. Все в общем формате `{code, detail}`, а не простым текстом.
  - **Мало запросов на страницу.** Каждый запрос к базе — это сетевой круг, до удалённой базы десятки миллисекунд.
    - То, чего у трека или альбома одно (исполнитель, альбом, обложка), приходит в том же запросе (`joinedload`). Отдельным запросом идут только участники трека.
    - Главная собирает альбомы всех полок одним запросом.
    - Страница исполнителя берёт его альбомы и альбомы, где он участвует, вместе.
    - Ссылка на поток читает трек с его перекодировкой одним запросом.
    - Соединение проверяется, только если оно простояло больше 10 секунд, а не перед каждым запросом.
    - Итог: главная — 7 запросов вместо 22, альбом — 6 вместо 13, поиск — 7–10 вместо 13. Тест `test_query_counts.py` держит эти числа.
  - **Поиск по индексам.** Нечёткое совпадение — это оператор `q <% name` (порог `pg_trgm.word_similarity_threshold` задаётся при подключении), а не вызов функции, поэтому его, как и `ILIKE`, отвечает trigram-индекс. Совпадения по имени исполнителя ищутся по его индексу отдельно и объединяются.
  - **Индексы под ссылки.** У каждого столбца, который ссылается на трек, альбом, исполнителя или обложку, есть индекс: удаление идёт каскадом, по одному запросу на строку, и без индекса каждый такой запрос читал бы всю таблицу. Ещё есть индекс прослушиваний по треку, для страницы исполнителя, и индексы задач по виду и по брошенным. Индексы строятся `CONCURRENTLY`, чтобы на большой базе не блокировать запись. Миграции не ждут чужую блокировку дольше 10 секунд, а ждущий своей очереди процесс опрашивает блокировку, а не ждёт её внутри транзакции.
  - **История ограничена.** «Недавно слушали» и главная смотрят только последние 2000 прослушиваний, а не всю историю, которая растёт без конца.
  - **Сжатие.** Ответы API в JSON сжимаются gzip, кроме потоков и картинок.
  - **Картинки обложек** отдаются без запроса к базе: сервер помнит, какому файлу соответствует обложка (обложка не меняется).
  - **Пароли** (argon2, ~0,1 с процессора) считаются в отдельном потоке, чтобы вход не замораживал остальные запросы.
  - **Большие изображения.** Картинка больше 40 миллионов пикселей не принимается. JPEG декодируется сразу в уменьшенном масштабе, и обложка хранится не больше 2000 пикселей по стороне.
- **Запись в библиотеку.** Загрузка в папку только для чтения или без прав отвечает `library_not_writable` (503), при кончившемся месте — `disk_full` (507), а не 500.

## API

Префикс `/api/v1`, интерактивная документация — `/api/docs`, схема — `/api/openapi.json`: всё серверное лежит под `/api`, остальные пути принадлежат web-клиенту. OpenAPI — контракт для web-клиента (генерация TS-типов) и KMP-клиента. Поле ответа со значением по умолчанию в схеме обязательное, потому что в JSON оно есть всегда. В запросах такие поля необязательные. Так сгенерированные клиенты получают точные типы.

Ошибки — всегда `{"code": ..., "detail": ...}`. `code` — стабильный идентификатор из перечисления `ErrorCode` (`invalid_credentials`, `track_not_found`, …): по нему клиенты показывают переведённое сообщение. `detail` — английский текст для разработчика, а у ошибок валидации (`validation_error`, 422) — список полей с `loc` и `type`.

## Клиенты (следующие фазы)

**Web (фаза 2):** React + Vite + TypeScript, TanStack Query, типы из OpenAPI, CSS `backdrop-filter` для стекла, `<audio>` + Media Session API. Код лежит в `web/`. Dev-сервер Vite проксирует `/api` на бэкенд, поэтому браузер работает с одним origin, как в продакшне, где сборку раздаёт сам сервер.

### Web-плеер

Один элемент `<audio>` на всё приложение (`web/src/player/player.ts`), состояние — в Zustand-хранилище, которое читают плеер внизу, «Сейчас играет», строки таблиц и кнопки «Играть». Логика очереди (`queue.ts`) — чистые функции с тестами; элемент `<audio>` в тестах заменяется подделкой, которая шлёт события так же, как браузер.
- **Поток.** Ссылка (`stream-url`) запрашивается в выбранном в настройках качестве. Браузеру без Ogg Opus (`canPlayType`) — сразу оригинал. Ссылку на следующий трек очереди плеер берёт заранее, пока играет текущий (и снова, если очередь поменялась), поэтому следующий трек начинается прямо в событии `ended`, без паузы на запрос: на телефоне в фоне это нужно, чтобы музыка не остановилась. Если ссылка истекает в течение минуты, перед продолжением берётся новая. Если поток оборвался (истёкшая ссылка, сеть), ссылка запрашивается заново один раз и трек продолжается с той же секунды; если и это не помогло, трек пропускается. После трёх неудач подряд плеер останавливается. Пропускается только трек, о котором сервер сказал, что его нет (`track_not_found`, `audio_file_missing`). На всё остальное — сервер не ответил за 15 секунд или вовсе, нет сети, 502 от прокси, пока сервер перезапускается, 503 — плеер останавливается на этом треке, а не листает очередь, и продолжает с той же секунды, когда сеть вернулась (событие `online`) или пользователь нажал «Играть». Пауза, нажатая, пока ссылка в пути, остаётся паузой. Ответ на запрос ссылки для трека, который уже не нужен (быстро нажали «Следующий»), отбрасывается. Пока плеер ждёт поток, вокруг кнопки «Пауза» крутится кольцо (`aria-busy`), если ожидание длится дольше 0,3 секунды. Смена качества в настройках применяется к играющему треку сразу. Когда начинает играть одна вкладка приложения, остальные ставятся на паузу (`BroadcastChannel`).
- **Скроббл.** Прослушиванием считается реально проигранное время, без перемоток и пауз: после 30 секунд (у трека короче минуты — после половины) плеер отправляет `POST /me/plays` со временем начала прослушивания (`played_at`). Прослушивание, которое не дошло до сервера (нет сети, 5xx, истекла сессия), хранится на устройстве (до 500 последних) и отправляется позже — после следующего удачного, при входе и при возвращении сети; так оно попадает в историю на своё место. Отправляет их одна вкладка за раз (Web Locks). Повтор трека — новое прослушивание, в том числе единственного трека очереди на повторе «все».
- **Очередь** хранится на устройстве (localStorage): после перезагрузки она на месте, на паузе с той же секунды. Позиция в треке хранится отдельно от очереди: она пишется раз в пять секунд, при паузе и при уходе со страницы, а очередь (это могут быть мегабайты) — только когда она сама меняется. Если очередь не помещается в хранилище браузера, сохраняются 500 треков вокруг текущего. Пишется только то, что изменила эта вкладка: скрытая вкладка не затирает очередь, которую сохранила другая. Сохранение старой версии читается (у версии 1 треки получают картинки альбомов), а сохранение, в котором треки не похожи на треки, отбрасывается, а не роняет приложение при каждом запуске. Когда администратор меняет обложку, треки в очереди получают её сразу. При выходе из аккаунта очередь и неотправленные прослушивания стираются. Громкость — настройка устройства, она остаётся. Синхронизация очереди между устройствами — вместе с Android.
- **Media Session**: название, исполнитель, альбом и обложка на экране блокировки и в системных медиа-кнопках, оттуда же — пауза, переключение и перемотка.

### Моё в web

- **Лайки** (`web/src/likes/`) применяются сразу. Пока изменение в пути, оно стоит поверх поля `liked` уже загруженных страниц. Когда сервер его принял, поле меняется в самих загруженных данных (`setQueryData`, без перезагрузки), а наложение снимается: лайк, снятый потом на другом устройстве, виден, как только страница загрузится заново. Треки в очереди плеера обновляются тоже, поэтому после перезагрузки лайк на месте. Изменения одного трека, альбома или артиста уходят на сервер строго по очереди: иначе «лайк» и «снять лайк» могли бы прийти в обратном порядке. Если сервер отказал в последнем изменении, показывается то, что есть на сервере (последнее принятое им значение), — двойное нажатие без сети не оставит на экране лайк, которого на сервере нет. Снятое убирается из открытых списков «Любимые треки» и «Избранное» сразу (страницы после него сдвигаются, чтобы «Показать ещё» ничего не пропустило); добавленное появится там при следующем заходе. Длинный список, который сейчас не на экране, при этом сокращается до первой страницы: заход за ним — один запрос, а не все показанные прежде страницы подряд. Так же после прослушивания помечаются устаревшими главная и «История».
- **Плейлисты** (`web/src/playlists/`): перестановка и удаление трека видны сразу. Изменения одного плейлиста уходят по очереди, и плейлист от сервера заменяет показанный, когда пришёл ответ на последнее изменение. Если изменение не прошло, плейлист загружается заново. Один трек может быть в плейлисте и в истории несколько раз, поэтому строки таблицы различаются по `item_id` и id прослушивания, а не по треку.

### Поиск в web

- Запрос уходит через 250 мс после последней нажатой клавиши или сразу по Enter. Запрос, который перебил следующий, отменяется (`AbortSignal`), а прежние результаты остаются на экране приглушёнными, пока не придут новые.
- Лучшее совпадение выбирает клиент (`web/src/search/match.ts`) из первых артиста, альбома и трека: название, равное запросу, лучше начинающегося с него, а то — лучше слова, начинающегося с него. Сравнение без учёта регистра, ударений и разницы «ё»/«е», но «й» остаётся собой.
- Плейлисты свои и немногочисленные: их ищет клиент по уже загруженному списку.

### Администрирование в web

- **Прогресс скана** берётся из `GET /library/scan` (статус и импорты одним ответом); пока скан или его импорты не закончены, он и сводка задач запрашиваются раз в секунду, потом опрос останавливается. Когда скан, начатый или замеченный на странице, закончился, перезагружаются каталог, главная и поиск, а итог объявляется. Если скан ждёт обработчик дольше 10 секунд, страница подсказывает проверить, что worker запущен.
- **Загрузка** (`web/src/admin/uploads.ts`) — очередь вне React, поэтому она продолжается, пока администратор ходит по приложению, и останавливается при выходе. Файлы уходят по два, через `XMLHttpRequest` — только он сообщает, сколько отправлено. Обложки и тексты папки уходят раньше её треков, чтобы импорт их уже застал. После отправки статус импорта спрашивается раз в полторы секунды, пачками до 100 путей. Перетащенные папки читаются через `webkitGetAsEntry`, выбранные — через `webkitdirectory`. Скрытые файлы и то, что не музыка, не обложка и не текст рядом с треком, пропускаются ещё на клиенте. Пока файлы в пути, закрытие вкладки спрашивает подтверждение.

- **Правки и управление** (`web/src/edits/`): пункты в меню трека, альбома и исполнителя (отдельной группой, под чертой), меню жанра в шапке списка альбомов этого жанра и кнопка под текстом песни есть только у администраторов. После переименования, переноса или удаления треки в очереди плеера запрашиваются заново: изменённые обновляются, удалённые уходят из неё (играющий доигрывает). Объединённый альбом или исполнитель открывается на месте прежнего; страница альбома, в котором не осталось треков, сменяется альбомом, куда их перенесли, или списком альбомов. Загрузка в альбом или исполнителю — одна очередь вне React по одному файлу (`XMLHttpRequest` ради процентов), она продолжается и при закрытом окне; у каждого файла своя цель, так что смена названия альбома посреди загрузки не трогает уже стоящие в очереди. Исполнитель, у которого перенесли все альбомы и который нигде больше не участвует, исчезает — открывается тот, кому их отдали; после удаления исполнителя — список исполнителей, после переименования или удаления жанра — список альбомов под новым именем или без жанра. Диалоги открывает один провайдер в оболочке, как «Добавить в плейлист». Обложка загружается сразу после выбора файла или перетаскивания, без отдельного «Сохранить». После правки перезагружаются все списки, где видны обложки, а сообщения об успехе выводятся из самих мутаций, так что они появятся, даже если диалог уже закрыли.

**Android + Linux (фаза 3):** Kotlin Multiplatform + Compose Multiplatform, Ktor-клиент, blur — Haze. Android: Media3/ExoPlayer + `MediaSessionService`. Linux: VLCJ или GStreamer (выбрать прототипом), MPRIS через D-Bus.

### Дизайн

Минимализм + glassmorphism по референсу. Поправки:
- вторичный текст на стекле — проверять контраст WCAG AA (≥ 4.5:1);
- на Linux — без macOS-кнопок окна;
- мобильный лэйаут отдельный: нижняя навигация, полноэкранный плеер;
- размытие: Android < 12 и GNOME не умеют системный blur — размываем обложку внутри приложения;
- `cover_palette` из API — для тонировки фона под текущий трек: `average`, `dominant`, `muted` (спокойный), `vibrant` (самый яркий; `null` у серых обложек), `luminance`. Web берёт `vibrant` (у серых обложек — `dominant`), `dominant` и `muted`, приглушает их и кладёт тремя пятнами под стекло; акцент остаётся выбранным пользователем. На страницах альбома и артиста тот же приглушённый цвет обложки слабо подкрашивает верх панели. Как при этом держится контраст — в [roadmap.md](roadmap.md#фаза-2--web-клиент), абзац «Тема».

## Риски

- **Задержка до БД.** Postgres доступен по сети (~80 мс на запрос, ~1,3 с на новое соединение). Пул соединений обязателен; API лучше разворачивать рядом с БД.
- **Аудио на Linux в JVM** не работает «из коробки» — нужен прототип.
- **Большая библиотека** долго перекодируется. Оригинал доступен сразу, варианты появляются по мере обработки очереди.
