# Установка на сервер

Thule ставится одним Docker-образом: в нём сервер и собранный веб-клиент. Из образа запускаются два процесса. `server` раздаёт приложение и API на одном порту. `worker` выполняет фоновые задачи: добавление файлов, перекодирование, поиск текстов. Оба описаны в [docker-compose.yml](../docker-compose.yml).

Нужны Docker с Compose 2.20 или новее и около 1 ГБ на диске под образ (скачивается около 250 МБ, большая часть — ffmpeg).

## Первый запуск

```bash
git clone https://github.com/Nezhirn/thule-music.git && cd thule-music
cp .env.example .env
```

В `.env` заполните:
- `THULE_SECRET_KEY` — длинная случайная строка. Ею подписываются входы и ссылки на поток. Сгенерировать можно так: `python3 -c 'import secrets; print(secrets.token_urlsafe(48))'`;
- `POSTGRES_PASSWORD` — пароль встроенной базы;
- `MUSIC_LIBRARY` — папка с вашей музыкой;
- `PUID` и `PGID` — владелец этой папки, их показывают `id -u` и `id -g`.

Запуск со встроенным Postgres:

```bash
docker compose --profile local-db up -d --build
```

Откройте `http://<сервер>:8000`. Первым откроется создание администратора. Затем в «Администрировании» нажмите «Сканировать медиатеку». Музыку можно и загрузить прямо там: файлами или целыми папками альбомов.

### Свой Postgres

Подходит Postgres 13 или новее. Пользователь должен уметь создать расширение `pg_trgm`, или его заранее создаёт администратор базы. Укажите базу в `.env`:

```
THULE_DATABASE_URL=postgresql+asyncpg://USER:PASSWORD@HOST:5432/DBNAME
```

Запуск без профиля: `docker compose up -d --build`. Postgres на той же машине должен слушать адрес, доступный контейнерам: `localhost` внутри контейнера — это сам контейнер.

## Как это устроено

- **Порядок запуска не важен.** `server` и `worker` при старте ждут базу (до минуты), доводят схему до актуальной и проверяют папки. Миграции выполняет тот, кто успел первым; второй ждёт его на блокировке в базе и находит схему готовой. Неверный пароль или имя базы останавливают запуск сразу, с понятным сообщением в логе.
- **Папки** — обычные папки на хосте, Docker-томов нет:

  | Переменная | Папка | Что там |
  |---|---|---|
  | `MUSIC_LIBRARY` | `./library` | ваша музыка; загруженное через приложение — в её подпапке `uploads/` |
  | `SERVER_DATA` | `./data` | обложки, аватары, перекодировки |
  | `POSTGRES_DATA` | `./postgres` | база встроенного Postgres |

- **Права.** Контейнер стартует от root, отдаёт пользователю `PUID:PGID` папку данных и созданную им папку `uploads/`, и дальше работает от этого пользователя. Остальные файлы музыки владельца не меняют. Если в compose задан свой `user:`, образ ничего не меняет и сразу запускается от него.
- **Музыка только для чтения.** Если сервер не может писать в папку с музыкой (смонтирована с `:ro` или принадлежит другому пользователю), он стартует с предупреждением в логе. Скан и прослушивание работают, а загрузка отвечает понятной ошибкой. Так же сообщается кончившееся место на диске.
- **Веб-клиент** раздаётся тем же сервером. Файлы сборки сжаты заранее (brotli и gzip) и кешируются браузером навсегда: в их именах хеш содержимого. Страница приложения перепроверяется при каждой загрузке, поэтому новая версия видна сразу после обновления. Страница идёт с Content Security Policy: приложение ничего не грузит с других сайтов, а внедрённый скрипт не выполнится и не отправит данные наружу.
- **Документация API** — `/api/docs`, схема — `/api/openapi.json`, проверка живости — `/api/v1/health`.

## HTTPS и обратный прокси

Снаружи сервер лучше открывать по HTTPS через обратный прокси. Это нужно не только для шифрования: браузер даёт вкладкам договориться об обновлении входа (Web Locks) только по HTTPS. Сервер нужен прокси целиком, на корне домена или поддомена (`music.example.com`), а не в подпапке.

Caddy сам получает сертификат:

```
music.example.com {
    reverse_proxy 127.0.0.1:8000
}
```

nginx:

```nginx
server {
    listen 443 ssl;
    server_name music.example.com;
    # ssl_certificate …; ssl_certificate_key …;

    # Загрузка альбомов: файлы идут по одному, но FLAC бывает большим.
    client_max_body_size 2g;

    location / {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        # Загрузки идут на сервер сразу, а не копятся в nginx.
        proxy_request_buffering off;
    }
}
```

Когда прокси на той же машине, откройте порт сервера только ей: `HTTP_PORT=127.0.0.1:8000` в `.env`. Если прокси в другом контейнере или на другой машине, укажите её адрес или сеть в `FORWARDED_ALLOW_IPS`: тогда в логах будут адреса клиентов, а не прокси.

## Обновление

```bash
git pull
docker compose --profile local-db up -d --build
```

(без `--profile local-db`, если база своя). Миграции применяются сами при старте.

## Резервные копии

Сохраняйте базу и папку данных:

```bash
docker compose exec postgres pg_dump -U thule thule > thule-$(date +%F).sql
```

В папке данных (`SERVER_DATA`) лежат аватары пользователей, их иначе не восстановить. Обложки и перекодировки сервер сделает заново при следующем скане (`transcodes/` можно не копировать). Музыка — ваша папка, её вы бэкапите как обычно.

## Логи и проверка

```bash
docker compose logs -f server worker
curl http://127.0.0.1:8000/api/v1/health
```

## Без Docker

Сервер ставится как обычный Python-пакет (см. [README](../README.md#бэкенд)), веб-клиент собирается `npm run build` в `web/dist`. Команды:
- `thule serve` — приложение и API, с `THULE_WEB_PATH=…/web/dist`;
- `thule worker` — фоновые задачи;
- `thule migrate` — только миграции.

Нужны ffmpeg и Postgres.
