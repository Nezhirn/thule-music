# Установка на сервер

Thule ставится одним Docker-образом: в нём сервер и собранный веб-клиент. Из образа запускаются два процесса. `server` раздаёт приложение и API на одном порту. `worker` выполняет фоновые задачи: добавление файлов, перекодирование, поиск текстов. Оба описаны в [docker-compose.yml](../docker-compose.yml).

Нужны Docker с Compose 2.20 или новее и около 1 ГБ на диске под образ (скачивается около 250 МБ, большая часть — ffmpeg).

## Первый запуск

```bash
git clone https://github.com/Nezhirn/thule-music.git && cd thule-music
cp .env.example .env
```

В `.env` заполните:
- `THULE_SECRET_KEY` — длинная случайная строка. Ею подписываются входы и ссылки на поток. Сгенерировать можно так: `python3 -c 'import secrets; print(secrets.token_urlsafe(48))'`;
- `POSTGRES_PASSWORD` — пароль встроенной базы;
- `MUSIC_LIBRARY` — папка с вашей музыкой;
- `PUID` и `PGID` — владелец этой папки, их показывают `id -u` и `id -g`.

Запуск со встроенным Postgres:

```bash
docker compose --profile local-db up -d --build
```

Откройте `http://<сервер>:8000`. Первым откроется создание администратора. Затем в «Администрировании» нажмите «Сканировать медиатеку». Музыку можно и загрузить прямо там: файлами или целыми папками альбомов.

### Свой Postgres

Подходит Postgres 13 или новее. Пользователь должен уметь создать расширение `pg_trgm`, или его заранее создаёт администратор базы. Укажите базу в `.env`:

```
THULE_DATABASE_URL=postgresql+asyncpg://USER:PASSWORD@HOST:5432/DBNAME
```

Запуск без профиля: `docker compose up -d --build`. Postgres на той же машине должен слушать адрес, доступный контейнерам: `localhost` внутри контейнера — это сам контейнер.

## Как это устроено

- **Порядок запуска не важен.** `server` и `worker` при старте ждут базу (до минуты), доводят схему до актуальной и проверяют папки. Миграции выполняет тот, кто успел первым; второй ждёт его на блокировке в базе и находит схему готовой. Неверный пароль или имя базы останавливают запуск сразу, с понятным сообщением в логе.
- **Папки** — обычные папки на хосте, Docker-томов нет:

  | Переменная | Папка | Что там |
  |---|---|---|
  | `MUSIC_LIBRARY` | `./library` | ваша музыка; загруженное через приложение — в её подпапке `uploads/` |
  | `SERVER_DATA` | `./data` | обложки, аватары, перекодировки |
  | `POSTGRES_DATA` | `./postgres` | база встроенного Postgres |

- **Права.** Контейнер стартует от root, отдаёт пользователю `PUID:PGID` папку данных и созданную им папку `uploads/`, и дальше работает от этого пользователя. Остальные файлы музыки владельца не меняют. Если в compose задан свой `user:`, образ ничего не меняет и сразу запускается от него.
- **Музыка только для чтения.** Если сервер не может писать в папку с музыкой (смонтирована с `:ro` или принадлежит другому пользователю), он стартует с предупреждением в логе. Скан и прослушивание работают, а загрузка и управление медиатекой (переименование, перенос и удаление треков и альбомов меняют сами файлы) отвечают понятной ошибкой. Так же сообщается кончившееся место на диске.
- **Управление медиатекой меняет файлы.** Что администратор правит в альбомах, треках, исполнителях и жанрах, записывается в теги файлов; перенесённый трек переезжает в папку альбома, удалённый — вместе с альбомом, исполнителем или жанром — удаляется с диска. Теги умеет писать в MP3, FLAC, Ogg, Opus и M4A; у WAV, WMA и AAC их не поменять. Удалённое не вернуть — держите резервную копию музыки.
- **Веб-клиент** раздаётся тем же сервером. Файлы сборки сжаты заранее (brotli и gzip) и кешируются браузером навсегда: в их именах хеш содержимого. Страница приложения перепроверяется при каждой загрузке, поэтому новая версия видна сразу после обновления. Страница идёт с Content Security Policy: приложение ничего не грузит с других сайтов, а внедрённый скрипт не выполнится и не отправит данные наружу.
- **Документация API** — `/api/docs`, схема — `/api/openapi.json`, проверка живости — `/api/v1/health`.

## HTTPS и обратный прокси

Снаружи сервер лучше открывать по HTTPS через обратный прокси. Это нужно не только для шифрования: браузер даёт вкладкам договориться об обновлении входа (Web Locks) только по HTTPS. Сервер нужен прокси целиком, на корне домена или поддомена (`music.example.com`), а не в подпапке.

Caddy сам получает сертификат:

```
music.example.com {
    reverse_proxy 127.0.0.1:8000
}
```

nginx:

```nginx
server {
    listen 443 ssl;
    server_name music.example.com;
    # ssl_certificate …; ssl_certificate_key …;

    # Загрузка альбомов: файлы идут по одному, но FLAC бывает большим.
    client_max_body_size 2g;

    location / {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        # Загрузки идут на сервер сразу, а не копятся в nginx.
        proxy_request_buffering off;
        # Переименование жанра или исполнителя с тысячами треков переписывает теги каждого
        # файла и может идти минуты: без этого nginx через 60 секунд ответил бы ошибкой,
        # хотя сервер работу доделает.
        proxy_read_timeout 15m;
        proxy_send_timeout 15m;
    }
}
```

Когда прокси на той же машине, откройте порт сервера только ей: `HTTP_PORT=127.0.0.1:8000` в `.env`. Если прокси в другом контейнере или на другой машине, укажите её адрес или сеть в `FORWARDED_ALLOW_IPS`: тогда в логах будут адреса клиентов, а не прокси.

## Обновление

Перед обновлением сделайте копию базы (см. ниже): миграции меняют её схему, и вернуться на прежнюю версию без копии нельзя.

```bash
docker compose exec postgres pg_dump -U thule -Fc thule > thule-before-update.dump
git pull
docker compose --profile local-db up -d --build
```

Без `--profile local-db`, если база своя. Миграции применяются сами при старте.

Если новая версия чем-то не подошла и нужно вернуться на прежнюю, восстановите сделанную перед обновлением копию базы (как в «Восстановлении» ниже) и запустите прежнюю версию: `git checkout <версия>`, потом `docker compose … up -d --build`. Прежняя версия на базе, которую уже обновила новая, не стартует. В логе это написано прямо: «The database was brought up to date by a newer version of Thule».

## Резервные копии

Копировать нужно три вещи:

| Что | Как | Почему |
|---|---|---|
| База | `docker compose exec postgres pg_dump -U thule -Fc thule > thule-$(date +%F).dump` | медиатека, пользователи, лайки, плейлисты, история, тексты |
| `SERVER_DATA/covers/` | любым копированием файлов, вместе с базой | обложки, которые выбрал администратор, фото исполнителей и аватары есть только здесь |
| Музыка | как обычно | теги в ней меняет управление медиатекой; удалённое приложением не вернуть |

`SERVER_DATA/transcodes/` копировать не обязательно: пропавшие перекодировки сервер сделает заново, когда трек начнут слушать, а пока будет отдавать оригинал. Обложки, взятые из файлов музыки, тоже выбираются заново, если их файлы пропали. Обложки и фото, загруженные вручную, без копии `covers/` не вернуть.

### Восстановление

Порядок важен: сервер и обработчик задач стартуют только на восстановленную базу.

```bash
docker compose stop server worker
docker compose --profile local-db up -d postgres
docker compose exec -T postgres dropdb -U thule thule
docker compose exec -T postgres createdb -U thule thule
docker compose exec -T postgres pg_restore -U thule -d thule < thule-2026-10-14.dump
# скопируйте covers/ обратно в SERVER_DATA
docker compose --profile local-db up -d
```

Если запустить сервер на пустой или чужой базе (ошиблись в адресе, база ещё восстанавливается), уборка не удалит обложки и перекодировки, которых эта база не знает: она пропускает папку, если таких файлов больше половины.

### Диск с музыкой

Если музыка лежит на отдельном диске или в сетевой папке, подключайте его до запуска контейнеров. Контейнер видит папку такой, какой она была при его старте, и подключённый позже диск не заметит, пока его не перезапустить. Пустую папку с музыкой сервер отмечает в логе при старте. Скан в этом случае ничего не удаляет: на странице «Медиатека» он сообщит, сколько треков не нашёл.

## Логи и проверка

```bash
docker compose ps                     # STATUS: healthy / unhealthy
docker compose logs -f server worker
curl http://127.0.0.1:8000/api/v1/health
```

У контейнеров есть проверка здоровья (`HEALTHCHECK` образа, раз в 30 секунд): сервер здоров, пока за 10 секунд отвечает на `/api/v1/health`, а тот спрашивает базу; обработчик задач — пока достаёт до базы (раз в 30 секунд он отмечает это в файле, проверка смотрит, не старше ли отметка двух минут). Первые две минуты после старта, пока применяются миграции, неудачные проверки не считаются. `unhealthy` у сервера — повод смотреть логи сервера и базы; у обработчика — что он не достаёт до базы. Причину последней неудачной проверки покажет `docker inspect --format '{{json .State.Health}}' <контейнер>`. Встроенный Postgres (профиль `local-db`) проверяется `pg_isready`, и сервер с обработчиком ждут, пока он не станет здоровым. Docker сам контейнер с `unhealthy` не перезапускает: это сигнал для вас или для мониторинга.

Логи каждого контейнера хранятся в трёх файлах по 10 МБ (`logging` в `docker-compose.yml`), старые удаляются сами.

Если папки `SERVER_DATA` или музыки лежат на сетевом диске, где root в контейнере не может менять владельца (NFS с `root_squash`, CIFS), старт не обрывается: в логе будет `entrypoint: couldn't make … the owner`, а сервер дальше сам скажет, может ли он туда писать и что сделать (обычно — выдать папку пользователю `PUID:PGID` на стороне сервера, где она лежит).

## Забытый пароль и блокировка входа

После 10 неудачных попыток за 15 минут вход под этим именем закрыт на четверть часа. Открыть его сразу или задать пароль, если администратор свой забыл, можно с сервера:

```bash
docker compose exec server thule unlock admin
docker compose exec server thule reset-password admin   # спросит новый пароль
echo 'новый-пароль' | docker compose exec -T server thule reset-password admin
```

`reset-password` выходит из аккаунта на всех устройствах и тоже снимает блокировку.

## Без Docker

Сервер ставится как обычный Python-пакет (см. [development.md](development.md#бэкенд)), веб-клиент собирается `npm run build` в `web/dist`. Команды:
- `thule serve` — приложение и API, с `THULE_WEB_PATH=…/web/dist`;
- `thule worker` — фоновые задачи;
- `thule migrate` — только миграции;
- `thule reset-password <имя>` и `thule unlock <имя>` — пароль и блокировка входа (см. выше).

Нужны ffmpeg и Postgres.
