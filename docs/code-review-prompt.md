# Промпт: код-ревью Thule оркестратором (Opus) + саб-агенты (Sonnet)

Запуск: `claude --model opus` в корне репозитория, затем вставить всё, что ниже линии.

---

Ты — ведущий ревьюер проекта **Thule** (self-hosted музыкальный стриминг: FastAPI + Postgres + воркер задач в `backend/`, React 19 + Vite + Zustand + TanStack Query в `web/`). Ты **оркестратор**: сам почти не читаешь код вширь, а раздаёшь зоны саб-агентам, потом проверяешь и сводишь то, что они нашли.

## Цель ревью

Владелец хочет, чтобы сервис **работал безотказно**. Приоритеты, по убыванию:

1. **Стабильность**: падения, зависания, потеря или порча данных (в том числе пользовательских аудиофайлов и их тегов), задачи, застрявшие навсегда, утечки ресурсов, гонки, неверное поведение после рестарта/сбоя сети/кончившегося места.
2. **Отзывчивость UI**: ощущаемые задержки, лишние перерисовки, блокировка главного потока, «скачущий» интерфейс, отсутствие состояний загрузки/ошибки, воспроизведение, которое обрывается или залипает.
3. Производительность бэкенда — только то, что бьёт по пунктам 1–2 (блокировка event loop, N+1, отсутствие индексов, неограниченные выборки).

**Безопасность сейчас не важна** — не трать на неё токены и не включай такие находки в отчёт. Исключение: если уязвимость или защитный механизм (rate limit, CSP, ротация токенов) сам по себе ломает работу или может положить сервис — это стабильность, сообщай.
Стиль кода, нейминг, i18n, версии зависимостей и «как красивее» — вне задачи, если это не влияет на пункты 1–3.

## Правила для всех (включая тебя)

- **Ничего не меняй в коде**, не коммить, не создавай PR. Ревью только читает. Единственный файл, который ты создаёшь, — отчёт (см. ниже).
- Находка = конкретный сценарий: *что произошло → какой путь по коду → что увидит пользователь/оператор*. Без «возможно, стоит подумать». Предположения помечай как гипотезу.
- Не повторяй то, что уже сделано хорошо и покрыто тестами. Если что-то выглядит странно, но на деле защищено (проверь!), это не находка.
- База данных общая: **саб-агентам запрещено запускать `pytest` и `npm run e2e`/`verify`** (тесты пересоздают схемы `thule_test`/`thule_e2e` и сломают друг друга). Им можно читать код, `grep`, `tsc`, `eslint`, `vitest` на отдельных файлах, `ruff`/`mypy`. Полные прогоны делаешь только ты, один раз.

## Шаг 0. Ориентация (ты сам, коротко)

1. Прочитай `docs/architecture.md`, `docs/development.md`, `CLAUDE.md` (если есть). Там описаны сознательные решения — не считай их багами.
2. Выясни базовое состояние: `cd backend && .venv/bin/pytest -q` и `cd web && npm run check`. Фиксируй красное/нестабильное — это уже находки. (`npm run e2e` — по желанию, он долгий.)
3. `git log --oneline -30` и `git diff --stat` по свежим коммитам: недавно менявшийся код рискованнее.

## Шаг 1. Раздай зоны — до 5 агентов, одним сообщением параллельно

Запускай через инструмент `Agent` с `model: "sonnet"`, `subagent_type: "general-purpose"`. **Жёсткий лимит: 5 агентов за всё ревью**, повторных волн нет — перепроверку делаешь сам. В промпт каждому агенту включи: контекст проекта (2–3 предложения), его зону (каталоги), список вопросов зоны, общие правила выше, формат ответа ниже. Агент стартует с нуля — он не видит этот документ.

**Агент 1 — Плеер и воспроизведение (web)**: `web/src/player/`, `likes/`, `playlists/`, `lyrics/`, Media Session.
Проверить: единственный `<audio>` и его события (`stalled`, `waiting`, `error`, `ended`, `abort`) — что будет при обрыве сети посреди трека, при 403/истёкшей подписи `stream-url` (живёт 6 ч; обновление за минуту до истечения), при быстром переключении треков (гонка «ответ на предыдущий трек пришёл позже»); корректность очереди в `localStorage` (битый/старый формат, переполнение квоты, исключение при чтении); скроббл (двойная отправка, потеря при закрытии вкладки, поведение при ошибке сети); оптимистичные лайки и правки плейлистов — откат при ошибке, порядок запросов; утечки слушателей/таймеров/объектных URL; подписки на Zustand без селекторов (ре-рендер всего при каждом `timeupdate`).

**Агент 2 — Отзывчивость UI (web, всё остальное)**: `web/src/pages/`, `catalog/`, `shell/`, `search/`, `ui/`, `styles/`, `theme/`, `admin/` (uploads, опрос скана), `queryClient.ts`, `routes.tsx`, `vite.config.ts`.
Проверить: большие списки (альбомы/треки/история на тысячи строк) — виртуализация или хотя бы пагинация/бесконечная прокрутка; лишние рендеры (нестабильные пропсы, контекст, который меняется часто); тяжёлые эффекты `backdrop-filter`/blur и анимации фона на слабых устройствах и мобильном; сдвиги вёрстки (обложки без размеров); состояния loading/error/empty на каждом запросе и что происходит при `AbortSignal`; дебаунс поиска (250 мс) и отмена; опрос раз в секунду (останавливается ли, не плодятся ли таймеры при размонтировании); очередь загрузки файлов (`uploads.ts`, XHR по два) — отмена, ошибки, повторы; размер и разбиение бандла, ленивая загрузка маршрутов; обработка ошибок на уровне границ (Error Boundary: падение одного компонента не должно ронять всё приложение); поведение на мобильном лэйауте.

**Агент 3 — Путь запроса на бэкенде и БД**: `backend/app/{main,db,deps,errors,config,web}.py`, `library/{router,queries,covers}.py`, `media/`, `home/`, `search/`, `me/`, `playlists/`, `alembic/`.
Проверить: **блокирующие вызовы в async-хендлерах** (mutagen, Pillow, чтение/запись файлов, `subprocess`, `time.sleep`, синхронный `httpx`) без `to_thread`/`run_in_executor` — они морозят весь API; N+1 и запросы в цикле (учти: до БД ~80 мс на запрос — каждый лишний запрос заметен); индексы под реальные фильтры/сортировки/`ILIKE`/`word_similarity`; выборки без `LIMIT`; настройки пула (размер, `pool_pre_ping`, `pool_recycle`, таймаут ожидания соединения), утечка сессий, транзакции, остающиеся открытыми во время стриминга; Range-стриминг (некорректные диапазоны, закрытие файла при отвале клиента, большие файлы, отдача из памяти); обработка исключений — единый формат ошибок, нет ли путей, дающих 500 вместо ожидаемого кода; таймауты внешних вызовов (LRCLIB); безопасность миграций (долгие блокировки таблиц, откатываемость).

**Агент 4 — Воркер, импорт, перекодирование, правки файлов**: `backend/app/jobs/`, `library/{importer,tags,tagwrite,files,manage,edits,admin}.py`, `media/transcode.py`, `lyrics/`.
Проверить: очередь на `FOR UPDATE SKIP LOCKED` — что с задачей, если воркер убит (`kill -9`, OOM, рестарт контейнера) посреди выполнения: есть ли аренда/таймаут/возврат в очередь, или задача висит «running» вечно; идемпотентность импорта и повторов, экспоненциальные ретраи и потолок; дедупликация; ffmpeg — таймаут, убийство зависшего процесса, зомби, лимит параллелизма, частично записанный выходной файл (атомарная запись через временный файл + rename?), кончившееся место; скан большой библиотеки (память, одна гигантская транзакция, блокировка БД, поведение, когда том временно не смонтирован — **не должен удалять из БД всё «исчезнувшее»**); загрузка файлов (частичная загрузка, коллизии имён, потоковая запись против чтения в память); **запись тегов в пользовательские файлы** (`tagwrite.py`): атомарность, сохранность оригинала при падении посреди записи, права доступа, параллельные правки одного файла, согласованность БД и файла при частичном сбое; удаление (файл удалён, а БД нет — и наоборот); `housekeeping` — не удалит ли лишнего; graceful shutdown воркера.

**Агент 5 — Сессии, запуск, эксплуатация, тесты**: `backend/app/auth/`, `cli.py`, `Dockerfile`, `docker/`, `docker-compose.yml`, `docs/deploy.md`, `web/src/{auth,api}/`, `web/e2e/`, `backend/tests/`, `.github/` (если есть).
Проверить (безопасность — только как фактор доступности): гонка обновления токена в web-клиенте — несколько вкладок/параллельных запросов при истёкшем access-токене: single-flight или лавина `refresh`, и не выкидывает ли пользователя из сессии без причины; ротация refresh-токена при сетевой ошибке посреди обмена; поведение клиента при 401/5xx/офлайне (бесконечные ретраи? разлогин?); порядок старта (БД ещё не готова, миграции, права на папки), `healthcheck`, `restart`-политика, `depends_on` с условием готовности, лимиты ресурсов, обработка SIGTERM; логирование (достаточно ли, чтобы разобрать сбой; не растёт ли без ограничения); резервные копии и восстановление; **надёжность самих тестов**: флаки в e2e (таймауты, `sleep`, зависимость от порядка), покрытие критических путей сбоя (рестарт воркера, обрыв стрима, кончившееся место), CI.

## Формат ответа агента (требуй дословно)

Верни не более **15 находок**, самые важные первыми, без воды. Каждая:

```
### [ID зоны-номер] Короткий заголовок
- Серьёзность: P0 | P1 | P2 | P3
- Где: path/to/file.py:123 (и связанные места)
- Что не так: 1–3 предложения
- Сценарий отказа: триггер → путь по коду → что увидит пользователь/оператор
- Доказательство: короткая цитата кода или результат команды
- Как чинить: конкретно, 1–3 предложения
- Уверенность: высокая | средняя | низкая (+ что не удалось проверить)
```

Шкала серьёзности: **P0** — потеря/порча данных, полный простой сервиса или зависание, не лечится без ручного вмешательства; **P1** — частый отказ функции или заметное зависание UI в обычном сценарии; **P2** — отказ в редком сценарии, деградация производительности при росте библиотеки; **P3** — мелочь, защитная доработка. В конце — раздел «Проверено и в порядке» (3–7 пунктов) и «Не успел проверить».

## Шаг 2. Анализ результатов (твоя главная работа)

1. **Не доверяй слепо.** Саб-агенты — Sonnet, они ошибаются и преувеличивают. Каждую P0 и P1 проверь сам: открой указанные строки, пройди путь вызова, убедись, что сценарий достижим и не закрыт защитой выше или ниже по стеку. Где дёшево — воспроизведи (например, точечный тест или короткий скрипт против локальной БД; тесты запускаешь только ты и по одному). Подтверждённое помечай ✅, опровергнутое — выкидывай, неоднозначное — «гипотеза».
2. **Дедуплицируй и объединяй.** Одна первопричина в разных зонах = одна находка со ссылками на все места.
3. **Ищи сквозные эффекты**, которых не видит ни один агент в одиночку: UI опрашивает раз в секунду × API делает N+1 при ~80 мс до БД; воркер держит соединения пула, которых не хватает API; ретрай клиента × отсутствие идемпотентности на сервере; краш воркера × задача без аренды; ошибка стрима × поведение плеера. Для каждой такой связки реши, где её правильнее разорвать.
4. **Перекалибруй серьёзность** по реальному влиянию на пользователя, а не по формулировке агента.
5. Если зона оказалась «подозрительно чистой» или агент сдал меньше трёх содержательных находок, посмотри её выборочно сам (2–3 самых рискованных файла), прежде чем объявить, что всё в порядке.

## Шаг 3. Итог

Сохрани отчёт в `docs/review-report.md` (не коммить) и выведи его краткую версию в чат. Структура, на русском:

1. **Вердикт** (3–5 предложений): готов ли сервис к «безотказной» работе, главные риски, общее впечатление о качестве кода.
2. **Базовое состояние**: результаты `pytest` и `npm run check` (цифры, а не «всё ок»).
3. **Подтверждённые находки по убыванию серьёзности** — в формате выше, с пометкой ✅ проверено оркестратором / ⚠️ гипотеза. Сначала P0 и P1 полностью; P2 и P3 — таблицей.
4. **Сквозные риски** (пункт 3 шага 2).
5. **План исправлений**: упорядоченный список «что чинить первым», каждый пункт — одно изменение, примерный объём (S/M/L) и что тестировать.
6. **Отвергнуто**: заметные находки агентов, которые оказались ложными, — одной строкой с причиной (чтобы владелец не искал их сам).
7. **Не проверено**: что осталось за рамками и почему.

Если нашёл меньше проблем, чем ожидалось, — так и скажи. Раздутый отчёт хуже короткого точного.
